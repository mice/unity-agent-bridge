# Multi-project routing and migration

Status: **2026-10-23 add-multi-project-routing 实施补丁，验收进行中未发布**.

This guide describes the current implementation checkout. It does not establish released behavior, completed real Codex acceptance, or compatibility between built-in tool contracts from different runtime versions. Existing frozen/release documentation remains the baseline until this increment is accepted and published.

## Start a connection with an explicit workspace

Build the runtime locally from the current source and use one host for the connection:

```powershell
& "D:/Tools/unity-agent-bridge.exe" mcp-server --routing-mode multi-project --workspace-root "D:/Work"
```

Equivalent environment settings are:

```text
UNITY_AGENT_BRIDGE_ROUTING_MODE=multi-project
UNITY_AGENT_BRIDGE_WORKSPACE_PATH=D:/Work
```

The command-line options override the environment values. Without an explicit workspace, direct host startup captures the working directory. Managed configuration generated by the updated Setup workflow includes the multi-project mode and workspace separately from the Unity project hint. Review the generated client configuration and reconnect the MCP client after applying it.

`UNITY_AGENT_BRIDGE_PROJECT_PATH` is a connection candidate hint in multi-project mode. It does not override the workspace default or authorize switching an existing task to that project. A workspace containing no resolved Unity project can still start the host and use local discovery; project execution then needs an explicit path.

An existing configuration with no routing-mode option or environment setting continues to use **single-project** mode. Updating the executable alone does not migrate that configuration. To migrate, prepare a current runtime, preview/apply a newly generated managed configuration, check its workspace and mode, and reconnect the client. Managed writers preserve unrelated servers and configuration fields. Keep the generated backup when migrating an existing file. An inherited routing-mode environment setting also affects old configurations, so inspect the actual launch environment when diagnosing unexpected mode selection.

## Choose the project for each new operation

Public project tools accept optional `projectPath` and `projectId` routing fields. For example, the MCP `tools/call` parameters for an explicit project are:

```json
{
  "name": "unity_editor_ping",
  "arguments": { "projectPath": "D:/Work/ProjectB" }
}
```

A relative `projectPath` resolves against the connection workspace. Explicit paths may select a project outside that workspace. The target must be an existing Unity project with a compatible, enabled Bridge and usable current Editor session. A bad path or unavailable explicit target produces an error; it does not fall back to another project.

Without a path, routing first selects the nearest Unity-project ancestor of the workspace. Otherwise it considers registered project paths within the workspace: zero candidates produces `PROJECT_NOT_RESOLVED`; multiple candidates produce `PROJECT_AMBIGUOUS`. Candidate selection does not discard offline projects to silently replace the intended default with an online neighbor.

`projectId` asserts the identity of the selected path. A disagreement with an explicit path produces `PROJECT_ID_MISMATCH`. An ID alone cannot select a different project; provide its path as well (`PROJECT_PATH_REQUIRED`). IDs derive from normalized physical local paths, with Windows case/link aliases normalized. Different checkouts have different IDs; moving a project creates a new path identity. IDs provide no cross-machine or cross-user identity inheritance.

## Registration, Editor availability, and readiness

A successful validated connection registers the project under the current local user. Saving client settings, installing the package, or discovering a Unity process does not register it. Registrations retain the canonical project path and the queue location actually used by the connection. Closing an Editor retains its registration and history.

The normal registry root is `%LOCALAPPDATA%/UnityAgentBridge/projects`. `UNITY_AGENT_BRIDGE_REGISTRY_ROOT` overrides it for isolated validation. Corrupt registration records do not prevent discovery of unrelated valid projects.

Call `unity_projects_list` to inspect registered sessions; use `{"includeOffline":true}` to include offline history. This is a local host query and does not dispatch a Unity command. `unity_editor_list` retains its separate process-discovery role and can find Editors that have never registered successfully.

Read the returned registration, `editorSession`, `availability`, `ready`, and `reason` together. Fresh matching PID/start identity, enabled Bridge, and heartbeat provide current availability evidence. Confirmed process exit produces `offline`; a stale heartbeat with a live or unconfirmed process produces a recovering/unknown observation, not proof of exit. The current freshness threshold is ten seconds. Discovery readiness is evidence at observation time; execution still checks lifecycle and the selected tool, and can reject a changed session or unavailable capability.

## Tasks, command handles, and offline reports

Ordinary calls, supported native MCP Tasks, and `unity_bridge_submit_only`/`unity_bridge_wait_result` use the selected project's queue and immutable ownership. A task or command handle remains bound to its original project, Editor session, and connection correlation. Ownership is persisted before dispatch/handle return; later lookups use that binding instead of the current default workspace. Selectors accompanying an existing handle must agree with it or return `TASK_PROJECT_CONFLICT`.

A submit/wait example uses these MCP tool arguments:

```json
{ "name": "unity_bridge_submit_only", "arguments": { "projectPath": "D:/Work/ProjectB", "tool": "unity.ping", "args": {} } }
```

Pass the returned `commandId` to `unity_bridge_wait_result`. Do not substitute the outer request's ID. Supported task clients use their advertised Tasks operations and returned task handles; availability of native Tasks depends on client negotiation.

The host's persistent ownership index delegates to project-local storage under `Library/AgentBridge`. Retained terminal results and owned report copies can be read while the original Editor is offline or after reconnecting the MCP host. Relative reports resolve against the original project. Retention is bounded (currently seven days plus capacity limits); expired, missing, corrupt, and unreadable data remain distinct failures. An offline Editor does not turn a retained terminal result into a new failure.

An active legacy record without an Editor-session identity is explicitly unconfirmed/unknown. A retained legacy terminal result can remain readable. The implementation does not assign an old active record to the new Editor, replay an outcome-unknown operation, or infer a failed test assertion from lost observation. `interrupted` requires evidence that the admitted instance ended; insufficient evidence remains outcome unknown. Cancellation responses describe observed/supported cancellation semantics and do not promise that a running Unity test has stopped.

## Session identity and lifecycle

`projectId` identifies the local project path. `editorSessionId` identifies one Editor process/start instance and survives Domain Reload; restarting the Editor changes it. `connectionId` identifies an MCP host connection and changes on reconnect. Historical bindings retain their original identities.

After reconnecting, querying an old task first must not transfer its connection identity to new work. New calls and submissions use the current host connection in their results and persistent routes; old tasks and reports read with their original task/command handle retain their originating connection. Missing historical connection identities remain unknown. This also applies when histories from several connections and projects are interleaved. Background maintenance observes original bindings without replaying user operations or allocating replacement tasks.

New versioned queue envelopes carry the expected project and Editor-session identities. The receiver checks them before execution and recovery; a replacement Editor rejects commands addressed to its predecessor. Reading an old saved terminal result does not require its session to match the current Editor.

Stopping A's Editor must not stop a host serving B. Project-level Stop excludes a known shared multi-project host; preparing/replacing a runtime in use remains blocked. Review every affected project before an explicit host-level shutdown. A runtime executable's location under A, or A's project hint, is insufficient evidence that the host belongs exclusively to A. With insufficient ownership evidence, inspect the host rather than treating it as a safe project Stop target.

## Current scope and validation limits

- Transport remains independent file queues per project. This increment does not deliver Socket transport or a separate permanent shared Host service.
- Multi-project routing builds the executable tool surface from the selected project's exported plugin catalog. Tools migrated from the historical built-in surface are available only when that target catalog exports them; absence is rejected rather than filled from the old host baseline. Same-name exports must agree with the baseline bridge-tool mapping and business schema constraints; incompatible contracts return `PROJECT_TOOL_CONTRACT_CONFLICT`, while reserved routing-field conflicts return `TOOL_ROUTING_FIELD_CONFLICT`.
- A separate core allowlist retains compile, task-template discovery/execution, scene opening, static-method execution, and diagnostics. These core tools require a matching current Editor-session identity, session schema version `1`, and a parseable `bridgeVersion` with major version `1` and version at least `1.4.3` (a prerelease suffix is removed for this gate). Otherwise invocation returns `PROJECT_PROTOCOL_UNSUPPORTED`. Local host tools remain independently available. This is a bounded protocol gate, not proof of compatibility with arbitrary runtime/package versions; the single-project catalog path keeps its existing behavior.
- A successful local protocol probe does not establish real Codex-session acceptance. Concurrent diagnostics, actual execution intervals, offline history, restart/reload, capability differences, and client configuration require reviewed acceptance evidence.
- Validation reuses the fixed A/B projects, creates no per-run Unity project, copies no `Library` cache, and holds the pair lease for live mutation. Fixture files and generated metadata are restored from exact preimages.
- Publication remains source-only and RC-first. This guide selects no release version and authorizes no publication or stable promotion.

For operational checks, see [MCP acceptance runbook](mcp-runbook.md). The workbench planning authority is `openspec/changes/add-multi-project-routing/` and `Documentation~/Unity_Agent_Bridge_Multi_Project_Version_Plan.md`; those repository artifacts and acceptance reports are not bundled into this package guide.


### Missing status and registration diagnostics

Discovery reads the current status snapshot on each request. Compiling, updating and explicit reload stages suppress readiness; a busy command stage is reported as `BRIDGE_BUSY` while unrelated bridge tools can remain available. This flag does not promise that the Unity Test Runner will admit another run.

`unity_projects_list` includes `registrationDiagnostics` for unreadable, corrupt or unsupported registration records. Healthy siblings remain discoverable; a malformed record is not silently treated as a usable project.

A graceful Editor exit can remove `Temp/status`. File absence alone never proves exit. For registered projects, the host retains one last verified Editor instance under the registry's `observed-sessions` directory, preserving exact PID and process creation time across host reconnects. Only evidence that this original instance has exited yields `offline`; a live or unobservable instance remains `recovering` with `ready=false`. Historical evidence never restores readiness. If there is no usable observation, discovery stays unknown. Observation writes do not register explicit candidate paths. These host-only focused regressions are pending execution and do not establish actual-client acceptance.
